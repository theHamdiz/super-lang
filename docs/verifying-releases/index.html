Quickstart

Verifying Super releases (0.1.0)

Checksums

Release bundles ship SHA256SUMS beside each archive on GitHub Releases.

curl -fsSLO "https://github.com/theHamdiz/super-lang/releases/download/v0.1.0/SHA256SUMS"
curl -fsSLO "https://github.com/theHamdiz/super-lang/releases/download/v0.1.0/super-0.1.0-x86_64-unknown-linux-gnu.tar.gz"
sha256sum -c SHA256SUMS

The installer scripts (install.sh, install.ps1) perform the same check before extracting into ~/.super/.

Each unpacked bundle also contains build-info.txt (commit SHA, rustc -V, UTC build stamp, and SOURCE_DATE_EPOCH when set).

GitHub build attestations (PARTIAL)

Tag releases from workflow release-bundle.yml attach a SLSA-style build provenance attestation for the aggregated SHA256SUMS manifest (not per-matrix archive attestations yet).

gh release download v0.1.0 -p SHA256SUMS
gh attestation verify SHA256SUMS --owner theHamdiz --repo super-lang

Per-archive gh attestation verify will be documented here once each tarball is attested individually.

Supported version

Security fixes are accepted for 0.1.0 only until a newer stable line is announced — see SECURITY.md.

Reproducibility

Release packaging sets SOURCE_DATE_EPOCH, remaps absolute paths, sorts tar members, and uses gzip -n. Full recipe and per-target claim table: REPRODUCE_BUILDS.md.

export SOURCE_DATE_EPOCH="$(git log -1 --format=%ct)"
export SUPER_VERSION=0.1.0
export SUPER_TARGET=x86_64-unknown-linux-gnu
./scripts/package_release.sh
scripts/repro_check.sh --target x86_64-unknown-linux-gnu

What this does not prove

Checksum verification does not audit compiler correctness, sandbox boundaries, or crypto implementations — see SAFETY_CLAIMS.md. Attestations prove which workflow produced SHA256SUMS, not that the Super language semantics are correct.
